## Project Overview

This is the official website for the Cal State LA University-Student Union (U-SU) — a student-facing portal for programs, events, services, and campus resources. Built with Next.js 14 (Pages Router) and deployed on Vercel.

## Commands

```bash
yarn dev          # Dev server (Next.js + next-video sync)
yarn build        # Production build (also generates sitemap)
yarn start        # Production server
yarn lint         # ESLint via next lint
yarn ts-lint      # TypeScript type checking (incremental watch)
yarn dev:sections # Dev server with section schema generation watching
```

Node version: 22.18.0 (use `nvm use`). Package manager: Yarn.

## Architecture

### Routing & Pages

Next.js Pages Router with file-based routing under `src/pages/`. API routes live at `src/pages/api/` and integrate with JotForm, Notion, Supabase, and Instagram. TypeScript `baseUrl` is `./src`, so imports are relative to that root.

### Component Organization

- `src/components/` — reusable UI primitives (Button, Card, Modal, Toast, etc.). Compose from these before creating new components — see "Reuse Before You Create" below.
- `src/modules/` — feature-based compositions (EventCard, BoardOfDirectors, Backoffice, etc.)
- `src/sections/` — full-width page sections (Hero, CTA, Instagram feed, etc.) with JSON schemas generated by `yarn generate-section-schemas`
- `src/partials/` — partial page layouts

### Styling

styled-components (SSR-enabled via `next.config.js`) + styled-system for spacing/layout props. Theme tokens live in `src/theme/`.

### State Management

- **Recoil** atoms in `src/atoms/` for global state (search results, events, editor, JotForm submissions, graphics requests)
- **React Context** (`src/context/ToastContext`) for toast notifications
- **NextAuth SessionProvider** for auth state

### Authentication & Authorization

NextAuth.js with Azure AD provider. `src/middleware.ts` protects `/backoffice` and `/graffix/backoffice` routes. Supabase maintains an allowlist of permitted backoffice users. Auth middleware uses JWT validation from next-auth/jwt.

### Code Quality

ESLint extends `next/core-web-vitals` + Prettier (single quotes, trailing commas). Husky + lint-staged enforce linting on pre-commit. TypeScript strict mode is on.

#### Naming

Name variables, props, and components after the concrete thing they hold, not a vague abstraction. Avoid generic catch-alls like `meta`, `data`, `info`, `config`, `item`, or `obj` when a domain-specific name fits — e.g. the hero's bottom detail rows are `details` (and `DEFAULT_DETAILS`), not `meta`. A reader should be able to tell what a name contains without tracing where it's used. Also avoid names that imply the wrong thing (`meta` reads as HTML `<meta>` tags). Prefer a longer, explicit name over a short ambiguous one; verbosity is fine when it makes the reference unmistakable.

### Testing

Jest + ts-jest. Run with `yarn test` (also runs as part of `yarn build`). Tests are centralized in `src/__tests__/` (not colocated), mirroring the source path under `src/`.

**API route tests** mirror the route under `pages/api/`, dropping the `pages/api/` prefix:

- Static segments stay as directories: `pages/api/bod/create.ts` → `__tests__/bod/create.test.ts`.
- `index.ts` collapses to its parent folder name: `pages/api/backoffice/users/index.ts` → `__tests__/backoffice/users.test.ts`.
- Dynamic segments lose their brackets and are dash-joined to the resource: `pages/api/backoffice/users/[id]/roles.ts` → `__tests__/backoffice/users-id-roles.test.ts`.
- A flat source route stays flat: `pages/api/jotformContact.ts` → `__tests__/jotformContact.test.ts`.

**Lib / helper tests** are named after the feature or function under test, not the file — because files like `lib/api.ts` hold many helpers. Example: `validateCalStateEmail` from `lib/api.ts` is tested in `__tests__/calstatela-email.test.ts`.

**Environment:** `testEnvironment` is `node` by default. A test that needs DOM/component rendering must opt in per-file with a `@jest-environment jsdom` docblock at the top.

**In-file style:** put `jest.mock(...)` calls before imports; group with `describe`/`it`; import internal helpers directly (e.g. `sanitize`, `validateContactForm`) to unit-test them without going through the HTTP handler. Imports use the configured module aliases (`pages/`, `lib/`, `modules/`, etc.), not relative paths — so moving a test file does not break its imports.

## Project Guidelines: Design System + Architecture

### Scope Discipline

Correctness comes first. When understanding the named files genuinely requires reading their direct dependencies — the callers that invoke them, the type definitions they rely on, the shared utils/atoms/theme tokens they consume — read those and briefly say why. The ban below is on _speculative_ and _repo-wide_ searches, not on the targeted reading a change actually needs. Patching a symptom in the named file when the cause lives one hop away is the failure this section exists to prevent on both sides.

Do not perform repo-wide or codewide searches unless explicitly instructed.

Before searching or refactoring, limit scope to the minimum set of files necessary for the task.

Default rule:

- inspect only the files named in the prompt
- if additional files are needed, expand scope narrowly and intentionally
- do not scan unrelated directories "just in case"

Forbidden unless explicitly requested:

- repo-wide audits
- broad/global searches across app, modules, routes, APIs, and pages
- speculative refactors outside the named scope

If a task is scoped to components, stay inside:

- `components/`
- explicitly named supporting files such as `globals.css`, theme files, or barrel exports

If a task is scoped to pages, stay only inside the directories named in the prompt.
Do not also scan unrelated components, routes, APIs, or other app areas unless explicitly required.

When refactoring a large area, work in narrow batches and only inspect the files needed for the current batch.

### Token Efficiency

Minimize token usage by avoiding unnecessary broad searches and repeated file reads.

Prefer:

- targeted file inspection
- narrow refactors
- focused summaries
- working directory by directory
- batching related files instead of scanning everything at once

Avoid:

- re-reading already-known files without a reason
- scanning entire directories when the task names specific files
- generating long exploratory audits unless explicitly requested

### No Parallel Explore Agents

Never spawn parallel explore agents when files and patterns are explicitly named in the prompt.
The prompt is the plan. Read one file, edit it, confirm, then move to the next.

Only use explore agents when the task requires genuine discovery across unknown files where the answer cannot be known upfront.

### Reuse Before You Create

Default to composing from existing primitives, not minting new ones. Before creating a component, search `src/components/` for one that already does the job (Button, Card, Modal, Typography, etc.) and use it — extending its props if it's close but not exact.

One-off components scoped to a single section/page are the exception, not the default. Only create a new component when the thing is genuinely reusable, or when a section's composition is complex enough to warrant extraction. A wrapper that exists solely to hold one block of section-specific JSX usually belongs inline in that section, not as its own file.

When a layout looks reusable, build it generic from the start: lift the variable parts to props (text, images, counts, variants) rather than hardcoding one section's content, so the next section can reuse it instead of spawning a near-duplicate. If you find yourself about to create a second component that is 80%+ the same as an existing one, generalize the existing one instead — and flag the duplication rather than quietly forking it.

Prefer prop-driven variants over new components for differences that are cosmetic (spacing, color, alignment). Reach for a new component only when structure or behavior genuinely differs.
